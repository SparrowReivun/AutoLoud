AutoLoud 重新定义了新时代的音量控制。无需学习，安装软件后，您仅需正常调节音量，它会自动学习您对响度的喜好，并智能地将未来所有声音控制在您舒适的响度区间，大幅减少反复手动调节音量的需要，同时保留优质内容原有的动态层次。

![AutoLoud 总览](assets/screenshot-dashboard.png)

## 为什么需要 AutoLoud？

你有没有想过，每天有多少次注意力被调音量打断？

打开一个新视频，声音突然变大；换一首歌，又轻得听不清。游戏里的对白刚刚调到合适的音量，下一场战斗却震耳欲聋。

我们反复调整音量，通常只是为了同一个目标：让声音听着舒服。

AutoLoud 希望让你直接表达这个目标。你通过熟悉的音量调整告诉它"我喜欢这么响"，它则在后续使用中持续学习和调整，让你把注意力留给内容本身。

## 下载与安装

1. 到 [Releases](https://github.com/SparrowReivun/AutoLoud/releases) 下载最新的 `AutoLoud-windows.zip`（约 100 MB，无需安装 Python）。
2. 解压到任意文件夹，运行里面的 `AutoLoud.exe`（整个文件夹要保持完整，exe 旁边的文件都是它需要的）。首次启动 Windows SmartScreen 可能提示「Windows 已保护你的电脑」——点「更多信息 → 仍要运行」。
3. 程序会自动打开校准向导，两分钟完成。之后它会缩到托盘里安静工作。

**关于杀毒软件报毒**：AutoLoud 没有代码签名（签名证书需要付费），而且它要接管音量键（全局键盘钩子）、采集系统回录、控制各应用的音量——这几种行为叠在一个没有信誉记录的新程序上，Defender / 360 等的启发式扫描有时会误判为木马。它是开源的，你可以对照源码或把 exe 传到 VirusTotal 核对；每个版本我们都会向 Microsoft 提交误报申诉。如果仍不放心，也可以按下文「从源码运行」自己跑。

界面随 Windows 显示语言自动选择中文或英文，可在设置页切换。

## 核心设计理念

### 1. 从操作驱动转向目标驱动

传统的音量控制依赖被动修正：听到声音过大或过小，再手动调整。每次操作解决的，往往只是眼前的问题。

AutoLoud 将音量调整视为偏好信息。你的操作既改变当前音量，也帮助系统理解你希望达到的听感，并将这一目标用于后续播放。

### 2. 稳定整体听感，保留动态层次

舒缓与高潮、轻声对白与激烈战斗，本来就应该有强弱之分。把所有声音都拉到同一个响度，会削弱这些差异，也容易让听感变得不自然。

AutoLoud 的目标是在减少不适的响度差异时，尽量保留作品原有的动态：

- 安静的段落依然安静。
- 激烈的场面依然有冲击力。
- 整体听感落在更舒适的范围内。

### 3. 多听少动

自动控制需要及时响应，也需要克制。短暂的爆炸声或一段轻声对白，不应立即触发整体音量变化。

AutoLoud 使用稳定态机制：新内容开始播放后，快速、平滑地寻找合适的增益；进入稳定态后，提高再次调整的门槛。

当前方案以约 2 秒为分析步长。只有连续多个步长都显示响度持续偏高或偏低时，系统才退出稳定态，重新调整。

持续分析，谨慎调整。

### 4. 学习响度分布，而非套用固定目标

同一个应用中也可能同时存在舒缓和激烈的内容。仅围绕用户偏好响度设置一个固定区间，仍然容易干预正常的强弱变化。

早期版本曾尝试将响度限制在较窄的固定区间内。实际测试促使项目转向结合历史响度分布的控制方式，让不同强度的内容拥有不同的目标响度。

AutoLoud 会逐步学习每个应用的历史源响度分布，再结合用户偏好，将不同响度层次映射到相应的目标区间。

### 5. 听觉保护

自动压低过响的声音，保护用户的听觉健康。

### 6. 按应用定制音量权限

帮助用户夺回对每个软件的声音控制权，尤其针对微信等通知音量过大、却不提供音量调节选项的软件。用户可以为每个应用单独、永久地设置音量偏好，彻底告别突如其来的铃声轰炸。此外，还提供丰富的功能定制接口，供高级用户深度使用。

### 7. 让每一位用户都能尽情享受声音的美好

甚至完全忘记音量调整和这个软件的存在。

## 工作原理

### 学习每个应用的响度特征

当只有一个应用发声时，系统可以回推去除全部增益后的源响度 L_src，并更新该应用的两个参考值：

| 参数 | 含义 |
| --- | --- |
| C_low | 历史源响度的第 20 百分位，代表较安静的响度层次 |
| C_high | 历史源响度的第 80 百分位，代表较响的响度层次 |

学习过程按有效发声时间计算，半衰期约为 20 分钟。这两个参考值可以在混音台中查看，也可以手动重学。

![AutoLoud 应用混音台](assets/screenshot-mixer.png)

### 计算目标响度

每个听音块结束时，系统计算当前源响度在两个参考值之间的相对位置：

```
u = clip((L_src - C_low) / (C_high - C_low), 0, 1)
T = (P - X) + X × u
```

其中：

| 参数 | 含义 |
| --- | --- |
| P | 用户偏好响度（human preference loudness） |
| X | 目标响度的变化范围 |
| u | 当前源响度在历史参考区间中的相对位置，限制在 0～1 |
| T | 当前目标响度（target loudness） |

当源响度接近安静参考值时，目标接近 P − X；接近响亮参考值时，目标接近 P。超过响亮参考值时，目标仍为 P。

这里限制的是目标响度。短时声音的实际表现还取决于控制器的响应和稳定态机制。

### 回退与重新学习

为处理学习不足、多个应用混音和应用内音量变化，当前实现采用以下规则：

| 情况 | 处理方式 |
| --- | --- |
| 有效学习时间不足 30 秒 | 暂取 T = P |
| 两个参考值相距不足 1 LU | 暂取 T = P |
| 多个应用同时发声 | 暂停源响度学习，保持上一次目标 |
| 连续 60 秒无法获得有效源响度测量 | 目标回退至 P |
| 源响度连续两分钟低于 C_low 超过 6 LU | 使用这两分钟的数据重建参考值，以适应应用内音量等变化 |

## Windows 音频工作原理（给开发者）

```
Windows 音频引擎 ──► 各应用会话混音 ──► WASAPI loopback 回录 ──► BS.1770 LUFS 实时测量
                          ▲                                                   │
                          │ ISimpleAudioVolume（每个应用的会话音量，≤ 0 dB）     │
                          └──────────────── 增益控制器 ◄───────────────────────┘
                                             │
                     IAudioEndpointVolume（主音量，只在需要"提升"时高于校准参考值）
```

- `autoloud/dsp/loudness.py` — 流式 BS.1770-4：K 加权、瞬时 / 短时 / 带门限的积分响度，与 pyloudnorm 对拍误差 < 0.2 LU。
- `autoloud/core/controller.py` — 纯逻辑的增益控制器（IDLE → ONSET → ADJUST → STEADY → SAFETY），可离线仿真。
- `autoloud/core/platforms.py` — 每个应用的源响度分布（C_low / C_high）学习。
- `autoloud/core/engine.py` — 回录 → 测量 → 决策 → 下发音量；主音量可见性探测；源响度回推。
- `autoloud/backends/windows.py` — PyAudioWPatch（loopback）+ pycaw（音量）；所有 COM 调用集中在一个线程。
- `autoloud/backends/mock.py` — 同接口的软件模拟器。
- `autoloud/ui/` — PySide6 界面：总览、校准向导、应用混音、设置、托盘。

这条「监听 + 控制音量」路线不替换音频流，所以做不了逐采样的限幅 / 压缩；换来的是免驱动、零延迟，并且天然知道是哪个应用在发声。`Backend` 接口已为将来的虚拟声卡后端预留。

从源码运行：`pip install -r requirements.txt && python run.py`；测试：`pip install -r requirements-dev.txt && pytest`。

## 日志

`%APPDATA%\AutoLoud\` 下：`autoloud.log` 是运行日志；`adjust-<时间>.log` 是每次运行的音量决策记录，和首页活动卡片同样的措辞，每行附当时在发声的应用；`meters-<时间>.csv`（每 100 ms 一行：瞬时 / 短时 / 窗口积分 LUFS、采样峰值、总增益、应用衰减、主音量提升、状态、P、主音量、当时唯一在响的应用、目标 T）和 `apps-<时间>.csv`（每 0.5 s、每个发声应用一行：峰值表、会话音量、总线增益、推子，以及该应用独自发声时去掉全部增益后的源响度 `src_momentary_lufs` / `src_short_lufs`）是原始测量数据，供分析。`volume-<时间>.csv` 记录用户的每一次音量操作（音量键 / 旋钮、P 滑块、推子、仅监测模式下的系统主音量变化）及当时的模式，用于统计有无 AutoLoud 时用户还要动几次音量。这些文件都不会自动清理。

想看某个应用在一次运行里的历史曲线：`pip install pandas matplotlib` 后运行 `python tools\plot_app.py ZenlessZoneZero.exe`（默认最近一次运行，可跟运行时间戳指定），会在当前目录生成 `<应用>-<时间>.png`，四幅图共用时间轴：该应用的峰值表（dBFS）与会话音量；总线的瞬时 / 短时 / 窗口积分感知响度与 P，绿色底表示那段时间只有这个应用在发声（此时总线响度就是它的响度——程序只测整体混音的 LUFS，没有逐应用的 LUFS）；该应用自身的源响度（去掉总线增益、推子、会话音量之后，即它在 100 % 会话音量、参考主音量下的响度；只有它独自发声的时段才有）；总线增益、推子与会话音量。

想比较「有 / 没有 AutoLoud 时用户自己动了多少次音量」：`python tools\plot_volume.py`（默认最近一次运行）会生成 `volume-<时间>.png`，上图是用户控制的电平——仅监测时段画 Windows 主音量（蓝）和每一次音量键（红）/ 滑块（绿）操作，自动预设时段画 P（橙）和每一次 P 滑块 / 音量键 / 推子操作；下图是 AutoLoud 自己的自动总增益（紫）与目标 T（绿虚线），仅监测时段为空，因为那时它不动任何音量；横轴下方标出 Chrome 当时的标签页标题（`--titles` 可换成别的应用），便于把每一串操作对上正在播放的曲目。

## 开发与测试状态

AutoLoud 仍在持续开发和调优中。

过去几周，项目累计投入两百多个小时进行开发、测试和迭代，形成了两个候选版本，并在游戏、音乐和视频场景中进行了数十小时的使用测试。目前，两个版本在已测试场景中整体表现良好。

在开发者的个人使用中，部分连续数小时的测试只需在开始时调整一次音量，之后无需再次手动干预。这是当前测试条件下的个人观察，尚不能代表所有设备、应用或用户的体验。

后续验证将重点关注：

- 手动调整音量的次数是否减少。
- 新内容开始后，进入稳定态需要多长时间。
- 是否出现突兀或不必要的增益变化。
- 对作品动态层次的保留程度。
- 多个应用同时发声时的控制效果。
